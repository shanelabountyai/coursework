Shane reviews, re-sequences and says go. The Phase 1 engines are the only place rules live; Phase 2 adds persistence around them and never re-implements a rule.

Phase 2 exit bar (PRD P0-6): a cycle-creating publish writes nothing; a tamper `UPDATE` fails; no stored progress column exists; every write names its actor and, where it applies, the catalog version; `course:eval` and `progress:verify` still pass unchanged against `fixtures/`, and a second `progress:verify` mode recomputes from the database and agrees with the fixture answers after a seed.

- [x] **2.1 Schema file and first migration.** `prisma/schema/coursework.prisma` (clone-owned per `foundation-drift.ts` `CLONE_OWNED`): `CatalogVersion` (id, label, `hash` CHAR(64), `content` JSONB = `{courses, equivalencies, certificates}`, `createdById`, `createdAt`, `orgId`), `Learner`, `Waiver`, `CompletionEvent` (learner, course, kind PASS/FAIL, `day` CHAR(10), `catalogVersionId`, actor), `Cohort` (course, `startDay` CHAR(10), scheme id, `catalogVersionId`), `ContentItem` (cohort, code, offsetDays), `Enrollment` (cohort, learner, status, `catalogVersionId`, `grandfathered` boolean + `grandfatheredMissing` text, V3), `ItemCompletion` (enrollment, item, `day` CHAR(10), verdict, actor), `GradeScheme` (JSONB, status, hash), `Assignment`, `Submission` (score_hp int, `submittedDay` CHAR(10), `supersedesId` nullable, `reason`), `PublishAttempt` (version from, edit JSONB, result, errors JSONB, cycles JSONB, grandfather report JSONB, actor). **Days are `CHAR(10)`, never `@db.Date`** (D-8; the lint already bans `@db.Date` in clone schemas). All tables carry `orgId` (foundation tenancy). *Acceptance:* `prisma validate`; migration applied from scratch in CI; `foundation:drift` clean (the file is clone-owned).
- [x] **2.2 Immutability triggers (hand-written SQL in the migration).** `UPDATE`/`DELETE` rejected on `CatalogVersion`, `CompletionEvent`, `ItemCompletion`, `Submission`, `PublishAttempt` (`RAISE EXCEPTION 'append-only'`), following the template's `audit_append_only` migration shape. A corrected score is a new `Submission` row with `supersedesId` and a `reason`; "current" is derived (`supersedesId IS NULL` and not superseded). *Acceptance:* tamper tests — a direct `UPDATE` on each table fails with the trigger's message; `prisma migrate reset` + `deploy` from scratch in CI.
- [x] **2.3 Schema test: progress is never stored (P1).** A vitest reads `information_schema.columns` for the clone's tables and asserts no column named like `progress`, `percent`, `eligible`, `eligibility`, `final_hp`, `letter`, `passed` exists outside `Submission.score_hp` and `PublishAttempt`'s JSONB report. *Acceptance:* the test; a planted `progressBp Int` column on `Enrollment` fails it (then remove).
- [x] **2.4 Publish through the engine (G5, V1).** `publishEdit(orgId, fromVersionId, edit, actor)`: load the version's content, `applyEdit`, `validateCatalog`; on `REJECT` write only a `PublishAttempt` row (edit, errors, cycles) and return the verdict; on `ACCEPT` write `PublishAttempt` + a new `CatalogVersion` with `hash = catalogHash(content)` + the G9 report (from live `Enrollment` rows and `CompletionEvent`/`Waiver`-derived `LearnerState`s), in one transaction. There is no other code path that inserts a `CatalogVersion` (non-negotiable 1): the Prisma call lives in one module and a test greps for it. *Acceptance:* E-01 writes one `PublishAttempt` and zero versions; E-04 writes a version whose hash equals the engine's and a report of 17 against a seeded book; the version's content re-hashes to its stored hash.
- [x] **2.5 Item completion through the engine (R1–R3).** `completeItem(enrollment, itemCode, day, actor)` builds the `Cohort` view from rows, calls `checkItemCompletion`, and writes an `ItemCompletion` with the verdict; `REJECT:*` writes the audit row and nothing else; course progress is a read (`courseProgressBp` over `ACCEPT` rows). *Acceptance:* the 154 + 12 fixture rejections, replayed, leave 154 + 12 refused rows and 1,885 accepted ones; progress for `C-ACC101-F26 / L-0003` reads 4444 with no stored number.
- [x] **2.6 Completion events and eligibility reads (G6–G8, V2).** `recordCompletion(learner, course, kind, day, versionId, actor)` append-only; `eligibilityFor(learner, versionId)` and `pathFor(learner, cert, versionId)` build a `LearnerState` from `CompletionEvent` + `Waiver` + the version's equivalencies and call the engine; re-evaluation against another version is a separate explicit call that returns both answers (P2, O-7 default). *Acceptance:* after seeding `fixtures/` into the database, `eligibilityFor` over 300 × 36 equals `expected_eligibility.csv` (0 diffs) through the database path.
- [x] **2.7 Gradebook reads and score corrections (S2–S9).** `gradeFor(cohort, learner)` builds assignments and *current* submissions and calls `gradeLearner`; `correctScore(submissionId, newScoreHp, reason, actor)` inserts a superseding row. *Acceptance:* 106 grades through the database equal `expected_grades.csv`; a correction changes the grade on the next read and leaves the old row untouched (tamper test on the old row).
- [x] **2.8 Seed from fixtures.** `npm run seed:fixtures` loads `fixtures/` (not `expected_*`) into the test database through the write paths above (so every row passes through the engines), tagged `cat-v1`; idempotent by refusing a non-empty org. *Acceptance:* run twice → second run refuses; row counts 40 / 7 / 2 / 300 / 24 / 1,352 / 16 / 341 / 2,051 / 35 / 806.
- [x] **2.9 `progress:verify --db`.** The Phase 1 command gains a mode that recomputes every enrollment and certificate progress from database rows and diffs the fixture answers. *Acceptance:* 0 diffs after `seed:fixtures`; one accepted `ItemCompletion` deleted via a superuser connection (bypassing the trigger) makes it report exactly one diff.
- [x] **2.10 Audit and actor.** Every write above goes through the foundation's audit log with the actor and, where it applies, the `catalogVersionId`. *Acceptance:* INV tests stay green; an audit row exists per publish attempt, completion, item completion and correction.
- [x] **2.11 CI.** Migrations applied from scratch on the runner's Postgres (already the template's flow); the tamper tests and the schema test are in `npm test`. *Acceptance:* green run linked in `NEXT.md`; `foundation:drift` clean.

**Not in Phase 2:** UI (Phase 3), outbox unlock notices (O-9, Phase 3), automatic re-evaluation on publish (O-7), minimum-grade prerequisites (O-3), cohort transfer, certificate issuance (P1 nice-to-have).

**Open for Shane before 2.1:** whether `Learner` is its own table or a foundation `User` (the brief's learners have emails on `example.org`; the foundation has magic-link users); whether to remove the billing module by the manifest in the same migration series (D-34 left it unwired); whether `CatalogVersion.content` holds the whole catalog JSON (simple, hash-checkable, 40 courses) or normalised `Course` rows (the PRD P0-1 wording says "`Course` rows with code, title, status, prerequisite expression as JSON") — the draft above keeps JSONB content for the hash and can add a derived `Course` projection table for querying if the UI needs it.
